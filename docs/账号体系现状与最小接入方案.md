# 技能商城账号体系现状与最小接入方案

> 审计日期：2026-08-30  
> 本轮结论：先停止开发登录界面和数据库改动。当前项目没有可复用的正式用户账号系统，直接增加登录页会变成假的登录状态。

## 一、当前现状

### 已存在

- 项目已经连接 Neon/PostgreSQL，环境中存在数据库连接变量。
- 目前只有“设计需求”接口在使用数据库，并会自动建立 `design_inquiries` 表。
- 创作九个入口已经存在；七个平台型入口与小说、短剧需要按不同路径分流。
- 小说的作品、章节、正文、人物和大纲已经进入同一份小说数据结构。

### 不存在

- 没有商城用户表。
- 没有注册接口、登录接口、退出接口和“当前用户”接口。
- 没有服务端会话表或安全会话 Cookie。
- 没有密码加密与校验流程。
- 没有按用户隔离创作数据的数据库表。
- 没有账号找回、邮箱验证或手机号验证能力。
- 项目依赖中没有 Auth.js、Better Auth、Clerk、Supabase Auth 等正式身份组件。

### 不能复用的界面

- “商家登录”明确写着界面预览，并且可以绕过登录直接进入商家后台。
- “管理员登录”点击按钮即可进入后台，没有真实身份校验。
- 以上两个页面不能改名后充当商城用户登录，否则只是伪登录，会造成数据和隐私风险。

### 当前创作数据保存方式

- 小说数据保存在浏览器 `localStorage`，主键为 `jiantu-novels-v2`。
- 其他创作通道也按通道名称保存在浏览器 `localStorage`。
- 当前数据只认浏览器，不认识用户；同一浏览器登录不同用户时无法保证不串数据。
- 当前订单和部分商城数据仍保存在项目本地 JSON 文件中，同样没有用户归属字段。

## 二、已确定的产品规则

1. 用户第一次进入 APP 时完成商城注册/登录，成功后进入商城首页。
2. 商城账号在首页、资源、创作、设计、我的之间共享，不重复登录。
3. “我的 → 申请入驻”是经营身份申请，不是注册第二个商城账号。
4. 微信公众号、百家号、知乎、头条、微博、小红书、读者属于外部平台型创作入口。
5. 小说、短剧属于商城内部创作，商城账号登录后直接进入对应创作区。
6. 外部平台身份只能由对应平台官方登录页或正式开放平台授权处理。
7. 商城不仿造第三方登录页，不接收第三方账号密码，不制作假的授权成功状态。
8. 商城登录页保持暖白、墨灰、细线、大留白和全中文。
9. 在正式账号和数据隔离完成前，不得用 `localStorage` 布尔值冒充商城登录。

## 三、最小正式接入方案

### 第 1 步：账号凭证（已确定）

- 手机号 + 验证码作为主要注册和登录方式。
- 邮箱不参与注册或登录，只作为数字商品收货邮箱。
- 正式开发验证码前，必须先确定短信与邮件服务商、费用、发送限制、有效期和防刷策略。

### 第 2 步：复用现有 Neon 数据库建立正式身份层

最小数据结构包括：

- `users`：用户身份、手机号、手机号验证状态、账号状态、默认收货邮箱和创建时间。
- `sessions`：随机会话、用户归属、到期时间和撤销时间。
- `verification_codes`：验证码用途、接收目标的安全摘要、到期时间、尝试次数和使用状态；不得保存可长期复用的明文验证码。
- 浏览器只接收 `HttpOnly`、`Secure`、`SameSite` 的会话 Cookie，不把身份令牌放进 `localStorage`。

最小服务端接口包括：

- 注册
- 手机号验证码登录
- 当前用户默认收货邮箱的读取与修改
- 退出登录
- 查询当前登录用户

### 第 2.1 步：用户长期记忆与偏好

长期记忆分成三类，不混在一个模糊的“用户画像”字段里：

- 必要资料：账号状态、验证状态、安全记录。
- 用户明确设置：常用创作通道、界面偏好、字体、主题、默认字数目标等。
- 经用户授权的行为摘要：常用功能、创作频率、偏好的工作方式和功能反馈。

长期记忆必须满足：

- 首次启用前明确说明用途并取得同意。
- 设置页可以查看、关闭、更正、导出和删除。
- 关闭后停止新增可选行为记录。
- 不记录密码、验证码、剪贴板、完整按键过程或与商城无关的浏览行为。
- 小说正文、人物和大纲不能直接当作行为画像训练材料；若未来需要分析内容，必须另行获得清楚授权。
- 产品升级优先使用匿名汇总数据，避免维护人员直接读取具体用户隐私。

### 第 3 步：APP 全局商城账号守卫

- APP 启动时由服务端会话判断是否已登录商城账号。
- 未登录进入商城自己的“注册 / 登录”页；成功后进入商城首页。
- 首页、资源、创作、设计、我的只使用这一套商城会话。
- 小说、短剧在商城已登录后直接进入内部创作区。

### 第 3.1 步：外部平台连接层

- 微信公众号、百家号、知乎、头条、微博、小红书、读者分别维护独立的平台连接状态，但不建立第二个商城账号。
- 优先使用平台正式开放授权；回调必须校验一次性 `state`，并只接受预先登记的商城内部返回地址。
- 商城不得展示仿造的第三方账号密码输入框，也不得把第三方凭证写入本地存储或数据库。
- 暂无正式授权能力时，只提供清楚标记的官方注册/登录入口，并保留返回商城的方法；不得显示“已授权”。
- “读者”确定为《读者》官网 `duzhe.com`；后续核实官方登录、投稿与开放能力。

### 第 4 步：建立用户创作数据归属

创作数据的服务端记录至少要包含：

- `user_id`
- `creation_type`
- `work_id`
- 内容数据
- 创建与更新时间

所有读取、修改、删除都必须在服务端按当前会话的 `user_id` 检查归属，不能相信浏览器传来的用户编号。

### 第 5 步：安全迁移当前浏览器小说

- 第一次登录后检测本机是否存在 `jiantu-novels-v2` 旧稿。
- 明确询问用户是否“把本机旧稿导入当前账号”。
- 用户确认后才上传，并为每部作品生成迁移记录，防止重复导入。
- 上传并核对成功前保留本机数据；不得先删除旧稿。
- 在同一浏览器切换账号时，不得自动把旧稿归到后登录的账号。

## 四、实施顺序

1. 确定短信服务商和邮件服务商，并配置正式发送域名与环境变量。
2. 建立正式用户、验证码、会话和身份接口。
3. 完成 APP 启动时的统一中文手机号验证码注册/登录页。
4. 保证五个一级页面共享商城登录状态，并把“注册入驻”文案统一改为“申请入驻”。
5. 将七个平台型入口改为“正式授权或官方入口”，将小说、短剧保留为商城内部直达。
6. 先保持现有小说浏览器数据正常可用。
7. 新建用户创作数据表和服务端归属检查。
8. 增加经过用户确认的旧稿迁移。
9. 增加可选择、可关闭、可删除的用户偏好与行为摘要。
10. 完成商城多账号隔离、验证码防刷、第三方授权回调和回归测试。

## 五、验收清单

- 退出商城账号 → 重新打开 APP → 出现商城注册/登录页。
- 商城登录成功 → 进入商城首页；五个一级页面不再次登录。
- 创作 → 点击知乎 → 进入知乎官方登录/正式授权，不出现第二个商城登录页。
- 返回创作 → 点击小说 → 不处理外部平台账号，直接进入小说创作区。
- 我的 → 申请入驻 → 提交入驻资料，不重新注册商城账号。
- 原有小说作品、章节、正文、人物、大纲和自动保存正常。
- 刷新页面后登录状态在有效期内保持。
- 退出登录后受保护的创作数据不可访问。
- 账号 A 与账号 B 的作品互相不可见、不可修改、不可删除。
- 非法 `returnTo` 不能把用户送到商城外部地址。
- 本机旧稿未经确认不上传、不改归属、不删除。

## 六、本轮明确未做

- 未制作登录页面。
- 未创建或修改数据库表。
- 未增加假的前端登录状态。
- 未改首页、资源、设计、我的及现有创作视觉。
- 未迁移或删除任何小说数据。

## 七、下一步需要确认

账号方式已经确定为“手机号 + 验证码”。邮箱只用于数字商品收货。正式实现前还需确定短信服务商和邮件服务商；在真实服务商可用前不得用固定验证码或伪造邮件发送结果。
